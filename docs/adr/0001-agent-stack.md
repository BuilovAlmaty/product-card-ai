# ADR 0001: Архитектура агентной системы

**Статус:** Принято  
**Дата:** 2026-11-06

## 1. Контекст

Разрабатывается агентная система для автоматической генерации карточек товаров с использованием LLM.

Система должна поддерживать:

- HTTP API для взаимодействия с клиентами.
- Выполнение бизнес-логики и оркестрацию AI-агентов.
- Подключение различных LLM-провайдеров.
- Хранение данных в реляционной базе.
- Векторный поиск для будущей реализации RAG.
- Автоматическое тестирование и проверку качества кода.

## 2. Архитектурное решение

Выбран следующий технологический стек:

| Компонент | Технология |
|---|---|
| Язык программирования | Python 3.12 |
| HTTP API | FastAPI |
| ASGI-сервер | Uvicorn |
| Работа с БД | SQLAlchemy + asyncpg |
| База данных | PostgreSQL 16 |
| Векторный поиск | pgvector |
| Агентная оркестрация | OpenAI Agents SDK |
| Конфигурация | Pydantic Settings |
| Управление зависимостями | uv |
| Контейнеризация БД | Docker Compose |
| Тестирование | pytest |
| Проверка качества кода | Ruff |
| CI | GitHub Actions |

Приложение разделяется на независимые по ответственности слои:

- `routers` — HTTP-интерфейс.
- `services` — бизнес-логика.
- `agents` — оркестрация агентов.
- `llm` — взаимодействие с LLM-провайдерами.
- `repositories` — доступ к данным.
- `schemas` — модели данных.
- `core` — инфраструктурные компоненты.

## 3. Рассмотренные альтернативы

**Django вместо FastAPI**

Django предоставляет больше встроенных компонентов, однако FastAPI лучше соответствует выбранному минимальному асинхронному API.

**MongoDB вместо PostgreSQL**

MongoDB позволяет хранить документы с гибкой структурой. PostgreSQL выбран благодаря реляционной модели данных и возможности использовать pgvector.

**LangGraph вместо OpenAI Agents SDK**

LangGraph предоставляет широкие возможности управления состоянием и графами выполнения. Для первоначальной реализации выбран OpenAI Agents SDK как более простой вариант оркестрации.

## 4. Компромиссы

Выбранная архитектура требует самостоятельно поддерживать:

- Конфигурацию приложения.
- Соединения с базой данных.
- Жизненный цикл ресурсов.
- Тестирование и CI.
- Интеграции с LLM-провайдерами.

Взамен получаем контроль над компонентами системы и возможность независимо развивать её функциональность.

## 5. Условия пересмотра

Архитектурное решение может быть пересмотрено, если:

- Агентные сценарии потребуют сложного управления состояниями и ветвлениями.
- Возникнет необходимость в распределённом выполнении длительных задач.
- PostgreSQL перестанет удовлетворять требованиям хранения и поиска.
- Появятся существенные ограничения выбранного SDK.
- Изменятся требования к нагрузке, безопасности или развёртыванию.

## 6. Последствия

На первом этапе реализуется минимальный каркас приложения.

В следующих этапах будут добавлены агенты, LLM, инструменты, бизнес-сценарии и RAG.

Новые инфраструктурные компоненты будут добавляться по мере появления конкретных требований.
